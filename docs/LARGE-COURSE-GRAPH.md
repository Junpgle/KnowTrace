# KnowTrace v1.6.0：章节内分组 + 跨章节桥接的3D关系图

## 按来源 PDF 快速归类知识点（推荐先完成）

如果你是**每个章节单独上传一份 PDF**，则无需先让 AI 学习关系再推测章节。

1. 打开「知识星系 · 3D → 按来源 PDF 归类」。
2. 系统从 `knowledge_point_sources → document_chunks → documents` 查询实际引用来源，列出有未归类知识点的 PDF 和每份文档涉及的点数。
3. 默认优先复用**名称与 PDF 文件名（不含扩展名）一致**的真实章节；若没有对应章节，可按文件名新建章节，也可以直接在预览里选择一个已有章节或修改新章节名称。
4. 检查对应关系，勾选确认后批量执行。仅处理原本 `chapter_id IS NULL` 的知识点，不覆盖手动归类结果。
5. 单 PDF 来源直接归入所选章节；多份 PDF 来源的知识点仅在**所有来源均完成映射且目标章节一致**时归类，否则留在未归类区待人工判断。无来源、存在未映射 PPTX 或其他资料引用的知识点也不会被猜测归类。
6. 批量归类不会修改知识点名称、摘要、证据、审核状态、掌握度或已审核关系；写入 `knowledge_point_events` 审计日志。重复执行不会重复移动已归类知识点。

预览与提交是两个独立 API，**GET 预览不会修改数据库**。批量确认接口为 `POST /api/courses/{course_id}/source-chapters/apply`，要求显式 `confirmed: true`，并逐份提供 `document_id` 和 `chapter_id` 或 `chapter_title`；所有章节和 PDF 必须属于当前课程。该操作不调用云端 AI。

> 注意：PDF 章节来源是一种可靠的组织线索，不等于证明知识点在学习上只有一个所属章节。跨文件复用的公共概念会被保留给人工审核；先修与跨章相关关系仍由关系工作台管理。

## 推荐流程：两轮构建，而不是全量两两比较

**第一轮：章节内相似组**。在「知识星系 · 3D → 提取 / 审核关系」中选「章节 + 相似知识点分组」，每组约12个点，先试运行30点。该轮主要确认章节内部相关/建议先修等关系。

**第二轮：跨章节桥接关系**。切换到「第二轮 · 跨章节桥接关系（推荐补全）」。页面会先免费显示真实章节数、未分章知识点数、来源文档数、跨章节候选组数和参与点次；**确认有候选组后**先试运行30个参与点次，检查生成质量，再扩大规模。跨章节规划采用：
1. 读取真实章节归属、课件文件及知识点名称与摘要；未归类知识点仅用真实课件来源分桶，不虚构章节。
2. 建立章节间共享术语的倒排索引，排除过于普遍的词素；优先跨章节匹配共同术语与共享来源。
3. 将最有可能相关的不同章节知识点放到同组，每组最多16个点，仅向AI提交有限原文片段。
4. AI识别先修、使用、相关、对比等候选关系；服务端对引用、来源ID与真实章节边界逐一核验。**不允许AI输出的同章边冒充跨章边**。
5. 完成一组即记录检查点。已完成的跨章节组合不会重复处理，但之前在章节内处理过的知识点仍可参加桥接；失败或服务重启后可手动恢复。
6. 在「集中审核已生成关系」按类型确认候选边，刷新3D星系。

**没有章节时怎么办**：如果1307个知识点均未归类，而且全部关联同一份课件，桥接预览会明确提示无法识别真正的跨章节边界，启动按钮将不可用。此时应先补充章节归属（或导入按章拆分的原始资料），不能靠名称相似虚构章节。即使知识点已经按页来源归类，当前预览仍不将页码当作真实章名。

**性能与局限**：这不需要1307×1307对知识点向AI逐一询问，但候选检索主要基于术语、摘要和课件证据的重叠，不等于真正的深度语义向量检索。跨章节但几乎没有词汇线索的隐藏关系可能漏掉；之后可加嵌入向量与章节级摘要桥接。是否存在先修关系最终由AI提供依据、人工决定，不由相似度自动确定。

## 操作路径

1. 进入「题库管理 → 知识点审核」，使用「信任模型结果 · 直接批量通过」。关系生成仅将已审核、有关联课件证据的知识点作为端点。
2. 打开「知识星系 · 3D」。图谱前端请求2000个节点，API最大支持2500，能加载包含1307个知识点的完整课程。星球使用Three.js InstancedMesh批量绘制。
3. 点击「提取 / 审核关系」，打开「整门课程 · 一键构建知识关系」。先选择章节内分组，完成后切换跨章节桥接。
4. 首选「章节 + 相似知识点分组（推荐）」策略，设置每组12个知识点，先试运行30点。系统优先按真实章节分桶；没有章节的点按原课件文件分桶；各桶内再按知识点名称、摘要、共享课件片段的相似度分组。30点通常拆成3–6个模型请求，具体取决于章节分布，而不是30次逐点调用。每组最多16点，且只使用有限原始课件文本。
5. 组内可以直接比较任意两个知识点，AI 最多建议18条关系；每条关系仍必须通过合法知识点ID、来源片段ID、至少10字符连续原文引用的逐条程序校验，才能保存为待审核关系。任务完成后，在「集中审核已生成关系」中按类型批量批准，严格前置会阻止循环。
6. 试运行满意后，选择剩余课程知识点规模，确认模型调用费用，再启动。已完成的知识点（包括旧逐点任务完成的）不会再次计费分析。支持整组完成后停止、续跑、服务重启恢复，进度显示已完成的知识点数和组数。
7. 刷新3D图谱；节点间金色语义连线只来自被批准的关系。课程/章节隶属线不是知识先修关系。

## 真实限制

- 推荐分组模式：理想情况下1307个点/每组12个大约109次模型调用，而不是1307次；实际章节分组、单点尾组可能使次数变化。输入文本会随组数增多，省下请求次数不等于一定同比减少Token费用。旧逐点模式仍可选。
- 分组使用轻量级中文字串/英文词汇重叠与共享课件片段，是**检索和聚类启发式**，不是 AI 语义嵌入；章节和相似性只决定哪些知识点一起交给模型，绝不直接生成边。当前还支持独立的跨章节桥接轮次，但只能召回有足够文本或课件关联线索的跨章候选，仍可能漏掉隐含前置关系。
- 未分类知识点仍可能聚在「未归类知识点」星系，现阶段没有自动章节分类。
- 每组只有1次直接的 MiMo 聊天补全调用（不走旧版逐点的反复 Function Calling），可明显减少往返延迟，但输出长度、模型负载与网络仍可能导致个别请求较慢。模型返回无效JSON会暂停，修复后恢复当前组。
- 后端运行依赖本地单进程线程模型，不支持多实例同时恢复同一个关系任务。
- 用户批量批准不代表AI提出的关系必定正确，建议先批准「相关、建议先修」，必要前置边更谨慎。

## 已运行旧的30点任务怎么办

若先前采用逐点生成、已运行了十分钟，不会因为拉取新代码自动切换为分组模式。可在旧任务点击「当前项完成后停止」，等待其停止并完成更新，选择「章节 + 相似知识点分组（推荐）」重新发起新的任务。已处理完成的焦点ID会从新任务规划中排除；停止前正在执行的那一次请求仍可能按云端实际规则计费。
